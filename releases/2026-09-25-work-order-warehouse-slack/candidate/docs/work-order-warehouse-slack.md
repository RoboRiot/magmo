# Work Order Add: warehouse Interiors and optional Slack delivery

## User flow

1. Choose a work order and movement direction, then scan items, bins, or pallets.
2. **Confirm list** opens a popup showing the movement and the item count.
3. **Yes, save changes** drains/stops the scanner relay and saves the inventory
   movement atomically, including each item's prior configuration and history.
4. Only after a successful save, a second popup asks **Send saved items to Slack?**
   Choosing No or closing this popup does not post anything or undo inventory.
5. Choosing Yes processes every unique saved item, including items expanded from
   bins/pallets. Current at work order uses **Shipping**; From work order uses
   **Receiving**. Each entry shows its delivery result.

Slack uses the same list columns, PN/SN, work-order number, tracking, description,
dates, photos, submitter attribution and Ops movement implementation as the item
page's Shipping/Receiving buttons. The saved operation's work order is used,
not whichever work-order entry happens to have the newest date. The existing
ten-photo limit is disclosed; photo or Ops attachment failures are shown as
warnings rather than hidden behind an unconditional success message.

## Warehouse defaults

Site-only warehouse work orders resolve to the established inventory client and
Interior machine. Exact verified identities are used; names and work-order titles
are not treated as identity evidence. The BlueFolder work-order client is kept in
the movement's provenance. This is an inventory endpoint default, not a merger
of client documents or a reassignment of machines/trailers.

Explicit machines/trailers and selected BlueFolder equipment take precedence.
Missing, deleted, conflicting or incomplete Interior ownership links block the
movement rather than silently reverting to site-only. Preview and confirmation
use the same default identities; confirmation revalidates the live records.

## Delivery safety

`POST /api/items/work-order-add/slack` accepts only `operationId` and `itemId`.
The server verifies authenticated internal access, operation ownership, successful
confirmation, exact saved membership, item movement history and current placement
before a first send. No client-provided Slack list, payload, row ID or actor is
trusted. The UI sends one item per request, sequentially, so a large list does not
depend on a single long-running bulk request.

Server-only receipts live below
`InventoryWorkOrderAddOperations/{operationId}/SlackItems/{itemId}`. A lease stops
concurrent duplicate clicks. The Slack row is checkpointed immediately after
creation. Failed field completion resumes that same row and original payload;
completed items are skipped. Inventory confirmation is never repeated to retry
Slack. If Slack might have created a row but its ID was not received, the receipt
remains uncertain and automatic recreation is blocked. Review Slack before any
manual recovery; do not clear the guard merely to make Retry available.

This change does not retroactively move items saved by older versions. No real
Slack messages or inventory movements should be generated by deployment tests.
Use mocked integration/browser tests and read-only production validation.
